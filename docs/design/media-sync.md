# 原图与缩略图完整下载后入库

状态：待实现。用户于 2026-10-13 将首版流程改为“缩略图与原图全部下载后再显示”。本页替代此前渐进下行设计，决策见 [ADR 0002](../adr/0002-complete-media-before-display.md)。

## 显示门槛

每张照片按以下流程处理，不需要等整个图库下载完成：

```text
接收元数据并保存同步待办（不进入可见图库）
  → 下载原图与缩略图到 staging
  → 分别校验摘要、大小、内容 generation
  → 准备兼容当前 ThumbnailLoader 的本地缓存
  → 稳定发布原图和缩略图、结算本地入库
  → 现有宫格显示本地缩略图
  → 点击后使用现有本地预览与原图解码流程
```

两个资源下载可并行，也可以串行；没有“先显示缩略图、以后再补原图”的成功状态。只有该照片的两个资源都稳定就绪才加入可见图库。

暂不实施远端占位项目、原图懒下载、按浏览/点击提升网络下载或单独的预览可见状态。未完成照片只留在同步清单与进度中。

## 服务端责任保持稳定

上传仍包含原图和缩略图；CPLMaster 资源描述与 CPLAsset/masterRef 采用受支持的子集，通过同 zone atomic 批次绑定。

每个角色有独立 AssetId、SHA-256、size、MIME 和尺寸；都必须 Published，并绑定同 content generation。缩略图声明 sourceOriginalSHA256，服务端与实际原图摘要核对。服务端不重新转码原图来证明视觉派生关系。

只改收藏或标题可复用原有两个资源。内容编辑需新资源对并执行版本条件。通用非照片 Record 不强制照片角色。

首版客户端生成缩略图并上传；JPEG/PNG、保持比例和方向、建议长边 1024、不超过 2048 与 2 MiB 的约束继续有效。宫格裁剪仍由 UI 完成。

## 最大化复用 PhotoViewer

本轮源码检查依据：`docs/modules/sync.md`；`src/core/sync/service/reconcile.rs` 的下载/发布/入库；`src/core/thumbnails.rs`、`src/core/thumbnails/cache.rs`；`src/ui/virtual_media_grid/factory.rs`；`src/ui/viewer/stage.rs`。

| 部分 | 接入方式 |
|---|---|
| media_items / MediaItem | 沿用真实本地 URI/path，未完成远端项目不进入该表 |
| 原图 staging、校验和原子发布 | 沿用同步发布/恢复机制，扩展为双资源就绪门槛 |
| LocalBackend / DbActor 入库 | 在两个资源稳定后沿用现有媒体入库事件 |
| 宫格和 SquareTile | 沿用 ThumbnailLoader 请求，不加网络逻辑 |
| 详情预览与原图解码 | 沿用当前本地预览→本地原图流程 |
| 编辑、删除、分享等本地操作 | 仍使用已发布原图，不引入“原图不存在”的常规分支 |

新工作集中在 Provider、远端增量清单/待办、双资源下载协调和缩略图导入。现有加载流程可大量沿用，但单文件下载执行器不能未经扩展就满足双资源门槛。

## 缩略图缓存导入

当前缓存按本地原图路径、mtime 和缓存版本定位，而非按远端 AssetId 直接定位。Small/Medium/Large 分别为 256/512/1024；缓存加载寻找内部 WebP/JPEG 文件。把下载图片放进任意目录无法自动命中。

计划在缩略图模块增加工作线程执行的导入边界：

1. 使用已校验缩略图、最终本地原图 URI/mtime 和绑定的 content generation。
2. 在后台按需要生成本地尺寸与编码，保持比例和方向，不读取原图重新生成预览。
3. 使用现有缓存键规则与原子缓存写入；图片内容不匹配、同 mtime 新内容或旧内存缓存需要精准失效处理。
4. 遵守现有 thumbnail_generated_at 与交付顺序，不通过任意置位冒充所有缓存已完成。
5. 入库后的宫格/详情仍调用当前 ThumbnailLoader 接口。

缓存导入属于适配工作，不要求 UI 自行理解远端 URL 或调用云端请求。

## 本地发布与恢复

客户端同步状态可记录 ManifestPending → Downloading → VerifiedPair → Publishing → LocalReady；只在同步存储中保存中间状态，不改可见媒体模型为半下载对象。

不存在覆盖两个文件和数据库的单一事务，因此要记录发布意图并恢复。原图最终路径对 scanner/watcher 可见前，两个下载都必须验证完成。缓存和原图发布、数据库入库可能交错，入库门槛也必须覆盖 watcher/scanner，不能因提前发现目标文件绕过 LocalReady。

实现可预先准备缓存再发布原图，并为尚在发布/恢复的目标登记索引屏障。屏障选择已固定为[客户端发布台账、统一索引准入和本地读取 lease](client-publication.md)；旧版本在 Publishing 中通过读取适配继续可用，LocalReady 的媒体/基线事务是提交点。现有机制尚未实现这些新增边界，需要 C1 测试证明。

任一资源失败时新照片不显示、不建立成功基线，已下载资源作为可恢复 staging 保留。现有照片更新失败时继续展示上一完整版本，不能把新缩略图和旧原图混用。

只有两个资源、缓存映射和入库结算完成才标记该照片同步完成。进度可显示下载中，但不把缩略图单项完成算作照片完成。

## 验收

- 元数据或单个资源到达后，新照片不在可见图库中。
- 两个资源都稳定后，每张照片逐项入库，不等待整个图库。
- 缩略图与原图不同 generation 或摘要错误，照片保持待办。
- 原图/缩略图失败或进程重启后，只继续缺失工作，不重复已验证资源。
- 现有版本在更新失败时可用，不出现混合版本。
- 监视器提前发现目标文件不能绕过双资源与发布门槛。
- 宫格命中导入缓存；点击不会触发对应原图网络下载，使用本地预览/原图路径。
- 缓存导入/失效/尺寸兼容有聚焦测试；PhotoViewer UI 使用真实输入验证。

## 下行优先与分类上行（新增约束）

[上行协调](../contracts/upload-coordination.md)固定正常下行 → 获取租约 → 锁内 token 检查/必要重新下行 → 删除/修改/新增。锁内资源重下行期间保活，原图/缩略图仍双资源完整后才显示；资源失败不进入上行。多端下行不会获取或等待上行租约。

metadata dirty 只改记录字段，不重传原图/缩略图；CONTENT dirty 上传变化资源，缩略图从同一稳定原图版本准备并原子绑定。dirty 直接来自本地 DB 字段，上行成功确认回调才更新，队列不是另存的 dirty。锁到期使当前及后续未完成上传全部报错；单资源完成/HTTP 200 中的失败项不能清整张照片的 dirty。
